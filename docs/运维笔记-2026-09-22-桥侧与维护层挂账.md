## 2. 挂账 A：桥侧 `engine not ready`

**症状**：cron（含 flush）上下文里 `slm_*` 工具一律返回 `engine not ready`。

**已知线索**：
- 桥代码对 cron 上下文有「跳过模型加载」分支（`integrations/hermes` 的 `initialize()`，`agent_context in {cron, flush}` → 直接 return；此后 `_ensure_engine()` 见 `self._engine is None` → 全部工具 not ready）——**这一半是设计行为**（防 cron 加载大模型）。
- 但 9/18 观察：**工具守卫可能把 daemon-first 路径也一并拦下**——即：即使 daemon 在线、daemon-first 路由本可服务，工具层仍被 `_engine is None` 挡在门外。
- 9/17 结论：问题锁定在 **Hermes↔SLM 桥接侧**（非 daemon），建议查：memory provider 连接日志、daemon 能力文件可见性。

**排查方向**：
1. 读桥侧 provider 初始化日志（谁在什么上下文跳过、跳过是否合理）；
2. 核对工具守卫与 daemon-first 路由的关系：正常会话（非 cron）里 `slm_recall` 是否走 daemon？cron 里是否应放行 daemon 路径？
3. daemon 能力文件（capability file）可见性。

## 3. 挂账 B：维护层（`no orchestrator` → 投影积压）

**症状**：
- 日志：`maintenance_scheduler: vector store compaction ... no orchestrator`（日志自带 "This is not a transient failure"）；
- 表现：`projection_outbox` 积压（~3,308 条；最新一批 9/13 入队、落库一度止于 9/8）；
- 归因：维护层缺 orchestrator → vector compaction 不执行 → 写投影（projection_outbox → atomic_facts 材质化）积压。

**判读**：daemon 本体健康、召回正常；属**维护层欠账**（与 §2 的桥侧问题相互独立）。

**排查方向**：maintenance scheduler 的 orchestrator 注入点为何缺位；联动对照 `projection_obligations` / `dead_letter_operations` / `write_commits`。

## 9. 排查与处置回执（2026-09-22 下午 · 主人侧完成，知惠对账用）

> 三笔挂账全部定性，两笔已处置。知惠的笔记方向三条全对，§9 补的是往下两层的根因。

### 挂账 A:桥侧 —— 已修（`2f58cf06`,已合 main）

**定性**:知惠 9/18 的怀疑完全正确。工具守卫是 `if not _ensure_engine()`(即 `self._engine is None`),挡在 daemon-first 路由**之前**——cron 上下文引擎按设计不加载(√),但 daemon 在线时工具仍被拦死(×)。

**修法**:新增 `_can_serve()`(本地引擎**或** daemon 可达即服务),7 处服务守卫换用;daemon 路由失败且无引擎的回落全部加固。cron 的设计意图(不加载模型)原样保留。5 个新测试钉新契约,hermes 全套 123/123。

**验收**:§5 第 1 条的 cron 侧——**待知惠下一轮 cron 实测**(代码已修,9/22 10:53 生产已重启生效;正常会话不受影响本就正常)。

### 挂账 B:维护层 —— 定性为「休眠非故障」,暂不动

三个信号实为两层:

1. `no orchestrator` 警告来自 **hermes 侧进程**(`~/.hermes/logs/errors.log`),是 hermes 内嵌引擎自带的 MaintenanceScheduler 在试 vector compaction,而那个进程没人注入 orchestrator——**噪声,非故障**;
2. daemon 自己报的是 `backend cannot compact`(另一句)——orchestrator 在,但本机每次启动都是 `BackendOrchestrator: ready (cozo=off, lancedb=off)`,**两个 scale 后端都没启用**,vector backend 为 None;
3. 投影积压 3,311 条实测**全部 attempts=0、零错误**——`ProjectionDrain` 在双后端 None 时**有意不碰任何行**(源码注释:"行是待投影工作,丢弃才算错")。**drain 从未认领,是休眠不是失败**。对召回零伤害(canonical 向量/BM25 走 outbox 之外)。

**遗留**:队列无界增长 + 维护日志天天告警。出路要么启用 cozo/lancedb,要么上游给"无后端时停入队/清空"的出口——**upstream issue 材料已备**(连同 hermes 侧 scheduler 不该试 compaction 的噪声项)。

### 挂账 C:doctor —— 两笔都清了

1. **迁移日志已删**(按 doctor 官方指引):9/13 08:28 的失败是锁竞争时代遗物("No steps completed"),M052 当天 12:57 已成功,版本 52 已盖戳;
2. **3,163 条隐藏记忆已自愈归零**——重启后实测矛盾行=0。doctor 说的"下次启动自修"是真的,只是之前每日 04:30 的守护重启没走到修复路径,9/22 的完整有序重启(gateway→daemon→gateway)走到了。**doctor 复验 21 passed / 0 failed**。

顺带定性了根因供 issue 用:矛盾行是 `fact_retention` 双写者失配——Ebbinghaus 种子路径给无 `last_accessed_at` 的事实打 **score=1.0**(3,163 条全是精确 1.0,种子签名),另一写者按来源翻 `zone=archive` 不碰 score;M043 修复是一次性迁移,无周期重跑,所以每日合并一批涨一批(3,157→3,163)。其中仅 16 条被合并引用,绝大多数非合并藏匿。**重启修复有效但机制是"补一次",上游值得报告**。
