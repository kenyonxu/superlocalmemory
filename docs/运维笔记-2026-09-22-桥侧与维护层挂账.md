## 2. 挂账 A：桥侧 `engine not ready`

**症状**：cron（含 flush）上下文里 `slm_*` 工具一律返回 `engine not ready`。

**已知线索**：
- 桥代码对 cron 上下文有「跳过模型加载」分支（`integrations/hermes` 的 `initialize()`，`agent_context in {cron, flush}` → 直接 return；此后 `_ensure_engine()` 见 `self._engine is None` → 全部工具 not ready）——**这一半是设计行为**（防 cron 加载大模型）。
- 但 9/18 观察：**工具守卫可能把 daemon-first 路径也一并拦下**——即：即使 daemon 在线、daemon-first 路由本可服务，工具层仍被 `_engine is None` 挡在门外。
- 9/17 结论：问题锁定在 **Hermes↔SLM 桥接侧**（非 daemon），建议查：memory provider 连接日志、daemon 能力文件可见性。

**排查方向**：
1. 读桥侧 provider 初始化日志（谁在什么上下文跳过、跳过是否合理）；
2. 核对工具守卫与 daemon-first 路由的关系：正常会话（非 cron）里 `slm_recall` 是否走 daemon？cron 里是否应放行 daemon 路径？
3. daemon 能力文件（capability file）可见性。

### 挂账 A:桥侧 —— 已修（`2f58cf06`,已合 main）

**定性**:知惠 9/18 的怀疑完全正确。工具守卫是 `if not _ensure_engine()`(即 `self._engine is None`),挡在 daemon-first 路由**之前**——cron 上下文引擎按设计不加载(√),但 daemon 在线时工具仍被拦死(×)。

**修法**:新增 `_can_serve()`(本地引擎**或** daemon 可达即服务),7 处服务守卫换用;daemon 路由失败且无引擎的回落全部加固。cron 的设计意图(不加载模型)原样保留。5 个新测试钉新契约,hermes 全套 123/123。

**验收**:§5 第 1 条的 cron 侧——**待知惠下一轮 cron 实测**(代码已修,9/22 10:53 生产已重启生效;正常会话不受影响本就正常)。

### 挂账 B:维护层 —— 定性为「休眠非故障」,暂不动

三个信号实为两层:

1. `no orchestrator` 警告来自 **hermes 侧进程**(`~/.hermes/logs/errors.log`),是 hermes 内嵌引擎自带的 MaintenanceScheduler 在试 vector compaction,而那个进程没人注入 orchestrator——**噪声,非故障**;
2. daemon 自己报的是 `backend cannot compact`(另一句)——orchestrator 在,但本机每次启动都是 `BackendOrchestrator: ready (cozo=off, lancedb=off)`,**两个 scale 后端都没启用**,vector backend 为 None;
3. 投影积压 3,311 条实测**全部 attempts=0、零错误**——`ProjectionDrain` 在双后端 None 时**有意不碰任何行**(源码注释:"行是待投影工作,丢弃才算错")。**drain 从未认领,是休眠不是失败**。对召回零伤害(canonical 向量/BM25 走 outbox 之外)。

**遗留**:队列无界增长 + 维护日志天天告警。出路要么启用 cozo/lancedb,要么上游给"无后端时停入队/清空"的出口——**upstream issue 材料已备**(连同 hermes 侧 scheduler 不该试 compaction 的噪声项)。

### 建议修复（供主人/上游）
1. `_daemon_available()` 加一次重试（如 2 次 × 2s、间隔 0.5s）——骑过瞬时噎住，不削弱 V3.7 身份校验；
2. 更根本：引擎 init 前先做快速 daemon 预检；daemon 在线（持 worker）时**跳过**内嵌引擎加载——消除 30s 挂起与「may retain model RAM」；
3. 小项：`_tool_status` 仍守 `_ensure_engine()`（引擎不可用时无法报 daemon 健康）——可评估加 daemon-health 回退。

### §10.1 补记：11:54 重测结果 —— 守卫已过，失败下移一层（daemon 召回延迟尖峰）

**第二发结果**：`{"error": "SuperLocalMemory daemon and engine both unavailable"}`（＝`_engine_recall` 返回 None），耗时 **9.02s**＝recall 客户端超时（`_DAEMON_RECALL_TIMEOUT = 8.0`）打满。
**关键**：报错文案换了——第一发卡在 `_can_serve()` 守卫（2.01s 签名），第二发**守卫已放行**（修复生效 ✓），失败落在 daemon 路由本身。

**daemon 侧实录（11:50–11:55，`~/.superlocalmemory/logs/daemon.log`）**：
- `Channel semantic/bm25/temporal/hopfield/spreading_activation did not finish within 8.0s` ×13；
- `recall: semantic recall exceeded 25s budget for '[ASYNC DELEGATION COMPLETE…]' — serving keyword fallback`（**大消息整段当 query**）；
- 同窗口大量 `POST /remember` + `Sheaf: N contradiction(s)` + `Temporal: proposed M correction(s)`；
- `Correction candidate not recorded … UNIQUE constraint failed: correction_cases.profile_id, correction_cases.predecessor_fact_id` **×152 / 10 分钟**（重复提议—失败循环，纯耗损）。

**定性（第三层根因）**：daemon 召回流水线在并发负载下超载——通道 8s 未完成、语义 25s 超预算降级；而**客户端预算（recall 8s）比 daemon 自己的预算（25s）还紧** → 负载高时客户端先放弃 → None →「both unavailable」。cron 会话只是恰好在最挤的时候到场。

**建议修复（更新版）**：
1. **客户端超时对齐**：`_DAEMON_RECALL_TIMEOUT` 8s → ≥30s（对齐 daemon 25s 语义预算＋余量）——单此一条，第二发就能过；
2. `_daemon_available()` 加重试（抗进程瞬时噎住）；
3. **修 `correction_cases` 重复提议**（去重/upsert，止血 152 次/10 分的空转）；
4. 超长 query 截断（大消息 → 取前 N 字符做 embedding）；
5. daemon 性能专项：语义通道为何稳超 8s（embedding 吞吐/并发）。

**当前实测（11:58）**：shell 复刻 daemon 召回 ✓（2.1s，3 条）；知惠会话 ✓（2.2s）——低负载时一切正常。

**小更正**：`~/.superlocalmemory/logs/daemon.{log,json.log}` **不再是死文件**（当前 daemon 正在写，11:58 仍活跃；`mslm_daemon_restart.log` 为 9/14–9/22 守护拉起期的重定向）。
